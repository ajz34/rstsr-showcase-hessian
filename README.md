## 抽象与去耦

请留意这份工作中，除去技术上的细节，最重要的部分是，使用 abstract class (python) 或 trait  (rust) 将 Hessian 的分量作分离 (去耦合)。这个去耦的过程尽管不复杂，但我也认为并非是 trivial 的。
- `RHessCoreAPI`：密度矩阵 0/1 阶量，一般是核排斥能、Hamiltonian Core。在 CP-HF 方程中，其作用只在 Hessian 中只对 $F_{p i}^\mathbb{A}$ 的 Fock 矩阵 Skeleton 导数作贡献。
- `RHessElecInteractAPI`：电子相互作用 (2 阶/高阶) 分量，一般是 Coulomb、Exchange、DFT 相关的分量。在 CP-HF 方程中，它还对 $A_{p i, q j} U_{q j}^\mathbb{A}$ 的 Fock 矩阵响应作贡献。
- 两个 Trait、以及 `RHessSCF` 作为统合的 Hessian 计算类型，其所有输入、输出参数都不包含分子信息，而只有张量信息。我不确定这么做是否有必要，但至少这是做得到的。因此，抛开具体实现的类型 `HessHcore` 或者 `RHessRIJKNaive` 等不谈，这个框架是不依赖于具体的电子积分库与 DFT 积分程序的、是普适的 (只要有一致的基函数定义，拿什么具体的程序实现都可以)。

这样之后，我们如果在未来要引入 DFT、溶剂化、外电场等其他分量，或引入特殊的性能优化，就可以在方法层面上去耦，而将强耦合的部分内聚到方法或算法优化内部，不去影响上面 Hessian 的计算主体程序。

目前 REST 在一阶梯度的代码中，为了引入新的分量，我们经常要在 RHF/RKS 或 UHF/UKS 实现相同/相似的代码。这其实不是最好的做法 (`trait GradAPI` 现在的情况是没有事实上被用上)；不过一阶梯度问题相对简单，如果未来有必要重构去耦，重构代价还是很小的。

二阶梯度问题本身要比一阶梯度复杂很多 (框架上不再是单独可以分离的量，而是需要用 CP-HF/KS 方程求解的问题；Sleketon 导数更复杂到我感觉顶不住，不过这是技术细节上的困难)。我认为去耦最好要在最开始就打好基础，否则后面要还的技术债很多；而 AI 如果自己对二阶梯度如何去耦没有概念 (过于细节的领域知识且似乎没有现成代码可以借鉴，我认为 PySCF 也不算完全适合)，框架设计这件事本身是不能完全依靠 AI 的。

去耦必须是有效的。必要的去耦确实会简化程序设计；但如果我们过度去耦了，以后程序的维护难度会反而比不去耦要更大，会把原来干净的代码瞬间变成更糟糕的屎山。需求是会发生变化的，去耦就将变化所需要的弹性扔掉了。所以现在只能相信我们的需求可以通过现在构造的几个不算复杂的 trait 就足够了。

> 目前该框架有一个缺陷：我们必须指定特定 device 的张量。当前项目要求使用 Faer 后端、REST 将会要求使用 OpenBLAS 后端。Trait 本身的设计可以引入泛型解决，但不同后端的具体实现再用 trait 的话会陷入 hell of trait bound。我个人认为这是没有银弹的：用哪个 BLAS、怎么用、要不要同时支持两个、怎么支持 GPU 这些问题本身就是复杂的，我总觉得各程序家家都有难念的经。
