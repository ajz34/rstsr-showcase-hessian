# 原型准备

我们工作本来的目标是要实现一个 Rust 版本的杂化泛函二阶梯度程序，以接入 REST 电子结构程序 (rust-based electronic structure toolkit)。但考虑到如下因素，我们需要一个特殊的原型实现工作。

本文档由人类完成 (非 AI 介入)。这份文档也是我自己先厘清思路的产物。对于 AI 来说，这份文档的主要作用是让 AI 先理解我们要实现什么样的程序、以及我们为什么要这么实现；而不是直接指导 AI 怎么实现。对于 AI 来说，真正指导 AI 怎么实现的文档，是在 .claude 文件夹下的 CLAUDE.md 文档。

## 原型工作一些重要决定

- **采用 Python 与 PySCF 作为起始验证**：我很长时间是使用 Python 与 PySCF 开发的用户，对它们非常熟悉。使用 Python 可以让我更快地迭代和验证算法的正确性。REST 电子结构程序在最初也使用 libcint 作为电子积分库，一般来说从数值结果上与 PySCF 有很好的一致性。

- **准备作一定的算法重构**：PySCF 目前在 resolution-of-identity (REST convention) density-fitting (PySCF convention) 下的算法，有可能是 sub-optimized 的。我们在原型阶段就打算作一些 FLOPs 数的计算与验证，在这一阶段重构与确定未来要在 Rust 程序下算法。

- **以工作时间序命名文件**：我们在原型阶段会有很多文件。这些文件将会以数字开头，表明我们的工作是如何从 0 开始，逐步迭代的。这个流程未来也许可以应用于其他导数性质、或其他电子结构方法的开发。如果 AI 难以跑通，这份流程也可以在我本人因各种原因无法维护时，其他人能以更高的效率接手维护。

    > 尽管这是我自大的猜测：尽管我现在对 Py-xDH 项目的代码风格和性能非常不满意，但它的文档、作为工作流程，或许确实帮助过一些研究者厘清研究和实现思路。
    >
    > 当时的 Py-xDH 更接近教材的写法，且当时的前提是没有可供使用的正确结果。这里我们已经有 PySCF 的正确结果，但最终的目标是彻底地确定程序性能问题、以及如何有效地迁移到 Rust 开发流程。目的是不同的，工作流也会不同。

    > 尽管我内心不愿意如此，但这个流程如果能让 AI 跑通，这份工作可以被炼化成 `同事.skill`；说老实话想到这还是很难受的，以后我们的职业技能将不再重要，我们的所有努力与付出真正成为了xx、资本与硅基生物的消耗品，甚至我们的工作不会被有效地 cite；而我们并没有什么对抗的手段。
    >
    > 无力的我们只是在这个时代中默默地被遗忘。pre-AI 时代也是如此，但它是以人的一生为长度的；但 AI 时代下，这就缩短到了年甚至月。这就是时代的洪流。

- **原型工作的目标**：
    
    - **规定一个特定小体系作为开发体系**。这个体系需要比较小、且最好不要是 3 个原子。后者的原因是，3 个原子就会有 3 个核梯度分量，导致我们在验证时需要对比 3 个分量的数值结果，增加了验证的复杂度。因此，我们考虑使用氨分子 (NH3) 作为测试体系。

    - **规定一个特定普通体系作为验证体系**。这个体系不需要很大，但需要有稍复杂的特征。特别是大多数原子需要在 x, y, z 三个分量上都要有非零的核梯度分量。同时，它应该要在一定程度上，能反映个人电脑上的性能情况。我们考虑使用乙醇分子 (C2H5OH) 作为验证体系。

    - **拆分计算分项**。我们需要把复杂的整体任务，拆分成一些相对独立的计算分项。这也要分两步走：第一步我们先要实现 Hartree-Fock 的梯度完整计算；第二步是杂化 DFT 的梯度完整计算。而每一步需要进一步拆分成一些相对独立的计算分项，包括 hamiltonian core (能量关于密度矩阵线性关系项)、Skeleton 导数中基组部分/辅助基/混合部分、CP-HF/KS 方程。

    - **分解计算到 RSTSR 可接受的算法**。在 Rust 下，我们将使用 RSTSR 作为替代 Python 下 NumPy 的高维张量库。在当前的二阶梯度计算任务下，NumPy 所需要的所有高维张量操作，RSTSR 下都有对应算法实现。关于这一点，我们将在未来的 CLAUDE skill 中说明，或我会先手动实现。但必须要注意，**我们要避免使用 einsum 操作**，以及要做好 row-major 迁移到 col-major 的准备。col-major 一定程度上是容易实现的 (我们只要在 Python 里把所有的高维张量都转置一下)。但不能使用 einsum，意味着高维张量需要分解为矩阵乘法；这个过程需要考虑指标连续性、并行粒度的问题。

    - **考虑并行粒度**。我们需要在 Python 原型实现时，就考虑如何在 Rust 下实现并行。但也留意，Python 原型实现可以不考虑并行本身。一般来说，如果遇到基组和辅助基都可以并行的情况，我们优先辅助基并行 (辅助基数量更大)。

    - **总体来说，原型工作很像 vibe plan 模式，迁移到 Rust 则是实际编写**。只是这个特殊的 "plan" 过程中，我们需要编写程序来验证算法的正确性和性能，而不是真的纸上谈兵。我们要在这一阶段就确定 Rust 代码的大致设计思路与接口。最终迁移到 Rust 的代码时，在明确的规则下，应该是接近一步到位的；只是这个规则由于现在还没有很清晰的 harness 文档，所以可能也会有一些不确定性；但大体思路上是这样的。

- **展望：以当前工作构建新的 harness**。这份工作完成后，我们或许也可以基于当前的 prototype 实现，构建 harness 文档，**在一些已经有其他程序具有正确结果的任务**，来指导未来的 REST 的开发。

    > 需要留意，**对于新的算法或电子结构方法**，即使该文档会有所帮助，但新的东西就是新的东西，不能指望 AI 将所有问题都解决清楚。
    >
    > 之所以类似于 NumPy 的科学计算程序的接口设计非常重要，是因为科学计算程序不仅仅承载性能问题，还需要让科研工作者以最快速度、最符合符号公式直觉的记号，**正确地**实现他们想要的功能。即使 AI 能提供帮助，但人的理解是最重要的。现在 NumPy 经常已经足够强大，经常情况是没有任何代码是无效的、任何代码都需要认真审查 (除非已经有正确的 test 数值，但“正确”这件事一来需要测试的充分性、二来新方法是没有办法提前知道正确数值的)；这与前端和一部分后端的情况是不同的。
